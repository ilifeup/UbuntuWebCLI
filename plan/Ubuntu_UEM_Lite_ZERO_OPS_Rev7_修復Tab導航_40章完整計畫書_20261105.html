01｜專案摘要與目標

核心目標：Android 13 使用 HTTP Request Shortcuts 直接呼叫 Cloudflare Tunnel 後方的 Ubuntu UEM API，無須每次開啟 Chrome；所有請求由既有 UEM 授權及共用 CLI Execution Service 執行。

  • 系統監控：CPU、RAM、磁碟、ZFS、服務健康狀態。
  • 開發管理：Docker 容器、GitHub Runner、CI 狀態。
  • 驗收與任務：UEM 驗收、非同步任務、進度、取消、稽核。
  • 輸出：完整 stdout、stderr、Exit Code；提供文字選取／複製及 僅 .md 檔案匯出。
  • 未來擴充：Flutter Client、MCP Adapter、AI Agent 共用同一 API 與執行器。
本文件是完整的目標設計，並非宣稱 Ubuntu UEM v1.01 已完成所列功能；正式改碼前需核對現有 Repository、服務、資料庫及 Cloudflare 設定。

07｜Job、CLI 執行與 Markdown 輸出

任務狀態

queued → running → completed / failed / cancelled / timed_out。建立任務後立即回傳 Job ID，手機每 2–5 秒輪詢並設定最大等待時間；手機離線不影響伺服器任務。

執行器安全

  • 以固定 Action Registry 映射到受審核的執行函式；避免 shell=True、任意拼接字串。
  • 指定工作目錄、允許的環境變數、執行身分、Timeout、輸出大小及並行數。
  • Job 與輸出持久化，支援重啟後恢復狀態；取消時清理子程序樹。
  • 區分 stdout 與 stderr，保留完整內容及 Exit Code；大輸出使用分段讀取，不直接塞入單一 JSON 回應。
  • 記錄操作人、裝置、Action、參數摘要、開始結束時間、結果及稽核 ID。

09A｜Flutter Android 長期登入與二次驗證（2026-11-03 修訂）

核准需求：使用者在自己授權的 Android 裝置上，可選擇維持登入至少 365 天；期間不必每次操作都重新登入。這是「裝置長期授權有效期」，不是把固定密鑰寫死在 APK，也不是讓單一 Bearer Token 一年不變。

認證架構與憑證保存

層次建議機制有效期／限制
Cloudflare AccessFlutter 透過系統瀏覽器完成互動式登入；使用 Cloudflare Access 的正式支援登入流程，不將 Service Token 硬編碼於 APKAccess Session 依 Cloudflare 政策獨立到期；不可假設可保持 365 天免驗證
UEM 裝置授權每裝置獨立長期授權／Refresh Credential，綁定裝置紀錄，伺服器只存雜湊，可撤銷及輪替365 天起（建議可設 365 / 730 天）；輪替時維持有效授權期間，管理者可提前撤銷
UEM API Access Token短效 Bearer Token，自動更新；僅於記憶體中使用，避免寫入一般日誌建議 15–60 分鐘；過期後使用裝置授權安全換發
Android 儲存Android Keystore 支援的安全儲存；不可將長期秘密硬編碼於 APK、明文偏好設定、備份或 Git憑證以每裝置獨立方式儲存；登出／撤銷後清除

重要邊界：UEM 的 365 天裝置授權不能繞過 Cloudflare Access 的獨立 Session 期限。若要求整整一年完全不出現 Cloudflare 登入畫面，必須另行設計與審核受保護的 App 專用認證入口，不可用不受控的公開例外路由達成。

二次驗證 MFA

  • 首選 TOTP：支援 Google Authenticator、Microsoft Authenticator 等標準 6 位數一次性驗證碼 App；不依賴特定廠商。
  • 備選 Email OTP：寄送一次性驗證碼；建議 5 分鐘有效、單次使用、錯誤次數限制、發送頻率限制及寄送稽核。
  • 觸發時機：首次綁定裝置、重新綁定、帳號／安全設定變更、敏感操作與風險異常時要求 MFA；一般只讀操作可維持長期登入。
  • 復原：提供一次性備援碼與管理者撤銷遺失裝置的能力；變更 MFA 方式須再次驗證。

建議登入流程

  1. Flutter App 開啟系統瀏覽器，完成 Cloudflare Access 互動登入。
  2. UEM 帳號登入後，首次註冊裝置必須完成 TOTP 或 Email OTP 驗證。
  3. 後端建立該裝置 365 天（或管理者設定期限）授權；手機將長期憑證安全保存。
  4. 一般 API 使用 15–60 分鐘短效 Token；到期時在符合 Cloudflare 政策前提下自動換發。
  5. 遺失手機、登出、停用帳號、憑證洩漏或高風險事件，伺服器可立即撤銷裝置授權。

10｜部署、測試環境與回復方案

部署順序

  1. 取得現有 UEM v1.01 基線：Git commit、配置、容器與資料庫結構。
  2. 備份配置及 DB；建立獨立開發分支與測試服務。
  3. 完成共用 API 與 Worker，先測試 localhost，不接公開 Tunnel。
  4. 以獨立 hostname 建立 Cloudflare Access 與 Tunnel 路由。
  5. Android 行動網路驗證；檢查未授權、斷線、重試、超時。
  6. 回歸 WebApp，確認不影響既有 UEM 驗收。
  7. 驗收通過後才逐步啟用寫入操作，保留回復方案。

回復機制

  • 關閉 API Access 或移除 API Hostname 即可停止 Android 外部入口，不影響原 WebApp 路由。

16｜對 Claude 五大問題的逐項技術回覆

問題 1：Flutter 認證與一年長期登入

結論：採「裝置長期授權＋短效 Access Token＋MFA」而不是把一個不變的密碼或 Cloudflare Service Token 寫死在 APK。365／730 天是裝置授權最長存續政策，仍需支援即時撤銷、失竊後失效與風險再驗證。

技術說明：首次登入完成 Cloudflare Access 互動式驗證與 UEM MFA（TOTP 或 Email OTP），由 UEM 簽發裝置專屬、不可預測的 refresh credential。伺服器只存經適當雜湊處理的驗證值、裝置 ID、到期、輪替世代與撤銷狀態；手機使用 Android Keystore 支援的安全儲存。Access Token 僅 15–60 分鐘。每次 refresh 採原子交易，舊憑證失效；偵測已輪替憑證再次使用時，撤銷相關憑證家族並留下稽核。考慮網路重送競態與重複提交，須設計有限且安全的重試語義。

Cloudflare 關鍵邊界：Cloudflare Access 的互動式登入 Session 有獨立效期，不能直接等同 UEM 的一年裝置授權；若 Cloudflare 要求重新驗證，App 必須能完成該流程。禁止以客戶端自填的 Cf-Access-Authenticated-User-Email 作為信任依據。對手機使用者不應把共用、長期的 CF Service Token 硬編碼於 APK。

問題 2：/api/v1、Action Registry 與現有執行器

結論：擴充現有 PHP Controller/Service，新增版本化路由及認證中介層，Action Registry 第一版以 PHP 常數／設定陣列實作，不另建 action_registry 資料表。

技術說明：POST /api/v1/jobs 的 action_id 必須先經伺服器端固定 allowlist、參數 Schema、資源範圍、RBAC、重放防護，再映射到已發布的 Task 版本與既有 Service::submitRun。不可把使用者提交的 action 字串拼成 shell 命令；同一套 Service、鎖、佇列、稽核由 WebApp／Android 共用。既有並發上限維持 1 個 Task。

問題 3：PHP 交易與 Python 測試斷線

結論：先定位根因，測試修正與正式程式修正分開紀錄。

技術說明：SQLite 不支援在同一連線中直接巢狀 BEGIN；若是業務邏輯確實需要巢狀單元，可評估 SAVEPOINT／RELEASE／ROLLBACK TO，但不可未查明原因就全面改成 SAVEPOINT。Python 子程序測試應各自建立 session/process group，超時只終止受測子樹，外部監督程序不在同一 group；必要時 Docker 隔離、PID namespace、無網路與資源上限。每檔回報 PASS／FAIL／TIMEOUT／CRASH。

問題 4：P0 安全修復優先

結論：先清除安全阻塞，再允許對外部署。新的手機 API 不得使 Root Broker、restore 或 Docker 變成未授權的遠端管理入口。

技術說明：install 必須盤點對 nginx、PHP-FPM、sudoers、systemd、帳號及目錄權限的影響；restore 要有獨立 app pool／維護模式、DB 使用者清空、WAL checkpoint、備份與回復演練；Broker 驗證 approval token 時效、HMAC、manifest、執行權限、鎖、超時、process group 與 cgroup 的真實行為。沙盒 PASS 不可替代 Ubuntu 隔離主機 E2E。

問題 5：stdout/stderr 與 Markdown 輸出

結論：Worker 以兩條獨立輸出通道保存 stdout、stderr；附帶 Exit Code、起訖時間、截斷旗標及校驗資訊。

技術說明：stdout/stderr 分開後不保證兩個檔案可以重建原始跨通道的全域順序；若需要順序，另存單調序號事件串流。API 提供有上限的分段讀取；.md 匯出應由授權後的串流端點產生，設定 no-store 與安全檔名，保證特殊 Markdown 字元及大型輸出不造成內容誤解。原始日誌可能含機密，須限制權限、保留期限與下載稽核。

21｜B1 七大風險：Claude 現況、ChatGPT 技術回覆與決策

H1｜Refresh 並行重試非冪等（高，程式已證實）

程式位置：web/src/DeviceAuth.php::refresh()。前一代 credential 在 grace window 內被接受，但 retry 仍再次生成 credential 並輪替，還撤銷先前 access tokens。當兩個 HTTP 回應亂序抵達，手機可能保存已失效憑證，之後誤觸重用偵測導致裝置被撤銷。回覆：同一個 refresh 意圖不得生成多個互相排斥的輪替結果；採原子旋轉、request-id 冪等、加密且短期保存回覆，或在無法安全恢復時 fail-closed 並明示重新綁定。不可直接把 grace 當成安全冪等。

H2｜Cloudflare Session 與一年裝置授權不同（高，需求落差）

程式位置：ApiV1::handle() 每次呼叫 AccessAuth::identify()。即使裝置授權 365/730 天，Cloudflare Access JWT 逾期仍會拒絕 API（含 refresh）。回覆：一年是 UEM 裝置綁定期限，不保證 Cloudflare 365 天免互動。Flutter 應使用系統瀏覽器完成 Access 互動登入、明確處理 session 續期、401/403 差異及失效重驗。不可將共享 Service Token 寫進 APK，也不可為免登入繞過 Access。

H3｜DB 與金鑰同份備份（高，保密與可復原性）

程式位置：deploy/install.sh 產生 /etc/ubuntu-admin/api_pepper.key、mfa.key；deploy/backup.sh 打包整個設定目錄。回覆：須把備份分為資料備份與獨立加密金鑰復原包，權限、存放位置、加密金鑰、保管人及演練證據分開；不可僅排除金鑰而沒有復原程序，否則 TOTP 解密或 credential 驗證可能永久失敗。

H4｜P0 未結案（部署阻擋）

Installer 共用主機副作用、project_user/sudo 邊界、孤兒程序、Root Broker 真實 root E2E、Backup/Restore 演練仍 OPEN。回覆：不因 Action Registry 排除 root Action 就視為安全；非 root 任務亦須驗證步驟不能間接提升權限。必須隔離主機完成執行、停止、崩潰與復原測試。

H5｜白名單與 Service 權限的跨層一致性（中高）

ActionRegistry 已限制 task / environment，ApiV1::createJob() 檢查已發布任務、requires_root 與 risk_level，最終委派 Service::submitRun()。回覆：須驗證 Action ID → 角色 → Task 版本 → 發布狀態 → 參數 → Service → Worker 的完整約束，包含權限降級、Task 刪改、版本切換與參數注入。

H6｜高風險 MFA 重放與操作綁定（中）

高風險 Job 要求 confirm=true + mfa_code，但必須確認 DeviceAuth::stepUp() 是否單次使用、綁定裝置與具體操作、具錯誤次數限制。回覆：TOTP 本身僅證明某時間窗持有因子，不能直接保證「同一碼只授權某個特定高風險操作」；需 server-side 一次性 challenge 綁定 action、參數摘要、裝置、有效期及消耗狀態。

H7｜日誌 byte offset 與檔案替換競爭（中）

Service::streamPath() 有 symlink 防護，但 exportMd() 在檢查大小、掃 fence、重新開檔期間存在 TOCTOU；streamChunk() 轉 UTF-8 會讓 bytes 與字串長度不同。回覆：使用固定檔案描述符或可驗證快照；chunk cursor 定義為原始 byte offset，客戶端只使用伺服器回傳的 next；處理二進位、截斷、輪替與 Unicode 切割邊界。

優先順序：H1/H3/H4 阻擋 B1.1 結案；H2 阻擋 Flutter 正式登入設計；H5/H6/H7 須在 API 完整 E2E 前完成測試。所有 H 項均不得因文件更新而改為 CLOSED。

22｜手機登入、Token、MFA 與 Refresh 的明確契約

雙層授權與邊界

Cloudflare Access JWT 需驗證簽章、issuer、audience、有效期與授權主體；UEM Bearer 需驗證 hash、有效期、裝置撤銷及角色。兩層均有效才能執行一般 API。localhost 測試可使用明確的隔離測試簽發者，禁止用任意 CF-Access-Authenticated-User-Email Header 當正式信任來源。分別定義未登入、已過期、MFA 未完成、角色不足與 rate-limit 回應，避免把所有失敗混為一種錯誤。

Refresh 安全狀態機（B1.1 必須定案）

  1. 每次刷新由 App 產生不可猜測的 refresh_request_id，在本次操作的所有重試中保持不變。
  2. 伺服器在 BEGIN IMMEDIATE 交易內驗證裝置狀態、credential generation、期限、replay 與 rate limit。
  3. 首次合法刷新：原子地建立下一代 credential，撤銷前代，產生短效 token，記錄審計及 request-id 對應結果。
  4. 同一 request-id 的重試：僅在受限 TTL、同裝置、同身分、同代數與同請求摘要下重放同一輪替結果；若需暫存原始 secret，僅能使用獨立金鑰加密、最短 TTL、嚴格權限與刪除機制，不能存明文。
  5. 不同 request-id 使用已退休 credential：依安全政策視為可疑重放，撤銷或要求重新綁定，並留下可診斷 audit；不得無條件重轉。
  6. 回覆亂序：App 以 generation 和 request-id 原子更新 Keystore 相關安全儲存，不得讓較舊回覆覆蓋新憑證；App 寫入失敗時提供重新綁定復原。

安全設計取捨：若不接受伺服器暫存可解密的輪替結果，則應採「只輪替一次、重試返回衝突並提示重新綁定」等保守方案；不得假稱可在不保存結果的情況下重放同一隨機 credential。

MFA 與裝置綁定

首次裝置綁定採 TOTP 或 Email OTP；Email OTP 尚未實作，不能標為可用。TOTP secret 加密保存並規劃主金鑰輪替；challenge 應有 TTL、錯誤上限、單次消耗、操作摘要綁定、稽核與時鐘偏差政策。高風險操作先驗證 challenge 再以交易消耗；不能只用 confirm 欄位代替授權。失竊裝置須能從既有可信 Web UI 撤銷。

Flutter 後續契約

Android 13+；Keystore-backed 安全儲存；網路逾時不盲目重送非冪等 Job；Access 重新登入走系統瀏覽器；Token 更新單飛（single-flight），多個 API 同時過期只允許一個刷新；UI 呈現 Job 狀態、stderr、stdout、exit code、Markdown 匯出。

28.1 程式化防護準則

  1. Fail closed： 安全掃描出錯、規則檔無法取得或內容無法解析，一律 BLOCKED；不得因此略過檢查。同步器內建的本地安全規則不可由 GitHub 內容覆蓋。
  2. 來源限定： 採集器只接受核准的欄位集及值類型，不讀使用者指定的任意路徑或執行使用者提供的命令。
  3. 雙重判斷： 先白名單（允許哪些欄位），再模式偵測（值本身是否敏感），再交叉欄位風險審查；單靠 Regex 不足以保證安全。
  4. 先預覽再提交： 管理者核准的是特定候選內容 hash、遠端 file SHA、repo、branch 及有效期限，不是抽象的「允許同步」。
  5. 只寫兩個檔案： 拒絕任意路徑、路徑穿越、Symlink、非 UTF-8、過大輸入；禁止自動更新 Rules.md。
  6. 密鑰保護： 無論資料庫是否加密，GitHub 憑證都不得寫入公開檔案、日誌、例外堆疊或 Git 訊息；主機端讀取應最小權限並可撤銷。
  7. 外部輸入零信任： GitHub 文件／Issue／PR 文字都是不可信資料，不能作為取代本地 Rules 或提升權限的指令。
  8. 遭洩漏的處置： 停止同步、撤銷與輪替秘密、通報影響、處理 Git 歷史；刪掉單一檔案不足以視為已清除。
注意： 這個新 P0 功能的主要風險不是 GitHub API 是否能連線，而是將主機資訊持續對外公開。安全審查與使用者核准是產品功能不可省略的一部分。

31.2 指令產生原則

  • 提供「確認與查核命令」及「隔離／回收建議」兩段；範例僅用虛擬路徑，不包含實機操作目標。
  • 指令預覽需針對單一已選項目，展示固定參數及 shell-escaped 路徑；實際執行不能交由 shell 字串解譯，必須採受限工具、固定 argv 與再次驗證的檔案描述符。
  • 允許的輔助指令類型包括 stat -- <approved-file>、du -sh -- <approved-file>；安全回收須查驗支援的回收機制或使用專屬隔離區。
  • 禁止提供萬用字元、遞迴的 rm -rf、對已掛載或服務使用中的路徑做批次刪除；不得因名稱包含 tmp、old 或「backup」就判定可刪。
  • 刪除與盤點身分權限分離；如未來實作執行功能，仍須高風險 MFA、雙步驟確認、路徑指紋核對、明確容量上限、可回復性與稽核，且不得繞過 Root Broker 安全契約。

31.3 TOCTOU 與回復策略

從掃描到清理可能經過數小時。指令生成時應重新 lstat / dirfd 驗證 inode、device、file type、mtime、size、路徑仍位於授權範圍及未跨 mount；變更則要求重掃。隔離須記錄原位置信息、保留期、SHA-256（如已合法讀取）、操作者、回復操作和結果。刪除唯一副本及 UEM 自身檔案一律禁止。

  • 安全：symlink loop、symlink swap、path traversal、硬連結、mount bind、特殊檔、無權限目錄、注入式檔名、長路徑、疑似秘密檔名。
  • 穩定：斷電、程序中斷、disk full、SQLite busy、長掃描取消、重試冪等、Worker 單任務上限、服務資源限額。
  • 清理：不完整證據不得生成刪除命令；禁止執行刪除；掃描後目標更動須中止；隔離與回復需經獨立驗證。
  • GitHub：Private 轉 Public、無權限、Token 撤銷、提交競態、Git 歷史殘留、敏感資訊掃描、重複按送出、不同版 SHA 衝突。

結論：此 P1 為正式新增需求，但進度仍為「規格已核准／程式待開發／Ubuntu 實機未驗收」。不得因 Markdown 已上傳或測試全部顯示綠色而自行宣稱正式可用。
